# Shared Room and Interaction

English | [简体中文](Room.zh-CN.md)

After the lobby has matched everyone into a session, any player can press the world-space **Enter Room** button. The whole session then enters a large room with a table; three objects on the table can be tapped (cycle color) and dragged (move), and every player sees the result.

## How it works

| Piece | File | Role |
|---|---|---|
| Unified pointer | `Assets/_Project/XR/PointerInput.cs` | One "look at it and pinch" input for every platform: visionOS gaze + pinch (PolySpatial `SpatialPointerDevice`, also mouse clicks in the visionOS simulator), XR controllers (aim ray + trigger: Quest, Meta XR Simulator), Meta aim hands (pinch), and the mouse in the editor (camera ray + left button). Dispatches Pressed / Dragged / Released / Tapped to the `PointerInteractable` under the pointer. |
| Interactable surface | `Assets/_Project/XR/PointerInteractable.cs` | Put on anything with a collider that should react to the pointer. A press that travels less than 3 cm is also a Tap. |
| Table objects | `Assets/_Project/Networking/NetworkInteractable.cs` | Tap cycles a color `NetworkVariable`; drag moves the owner-authoritative `NetworkTransform`. Whoever touches an object takes ownership first (Distributed Authority, `Transferable`), so taps made before the transfer completes are applied when ownership arrives. Hidden while the room is closed. |
| Room state | `Assets/_Project/Networking/RoomController.cs` | One `NetworkVariable<bool>` for the whole session. Any player's request goes to the owner via `[Rpc(SendTo.Owner)]`; every client then loads or unloads `Room.unity` additively on its own. The owner spawns the table objects the first time the room opens. |
| Button | `Assets/_Project/App/WorldButton.cs`, `EnterRoomButton.cs` | A 3D slab + label + collider driven by the pointer, now part of the lobby panel ([Lobby.md](Lobby.md)). Shows *Connecting...* until the session and the RoomController are up, then *Enter Room* / *Leave Room*. The voice commands "enter the room" / "leave the room" do the same. |
| Room scene | `Assets/_Project/Scenes/Room.unity` | Visuals only (no NetworkObjects): 12 × 12 m room, table at the centre of the seat circle, rug, shelf with books, pictures, plant, floor lamp, two point lights. Generated by **Tools → MR → Generate Room Content**. |

Design choices worth knowing:

- **No NetworkSceneManager.** The room scene holds no networked objects, so each client loads it locally and Distributed Authority stays untouched. The networked objects are spawned into the session and simply hide while the room is closed.
- **The whole session enters together.** In a shared space everyone should be in the same place; the button is a session-wide switch, not a per-player teleport.
- **The table sits at the seat circle's centre** (`SeatAssigner`), so players stand around it, and the Phase 0 probe cube now orbits above it at 1.9 m.
- **Session objects outlive their owner.** `DontDestroyWithOwner` is set on the RoomController, the table objects and the probe; without it Distributed Authority destroys an object when its owner disconnects instead of handing it to another client (found in testing: the room and two of three objects vanished when the session owner quit). `AppBootstrap` also re-spawns a missing RoomController when the local client is promoted to session owner.
- **Ownership before mutation.** Under Distributed Authority only the owner may write the color variable or the transform, so a tap by a non-owner first requests ownership (`ChangeOwnership`) and is applied in `OnGainedOwnership`.

## Testing

### Editor
1. Open `Main.unity`, press Play, wait for *Enter Room* to turn blue.
2. Click it with the mouse (left button; the right button is the fly camera's look). The room loads and three objects appear on the table.
3. Click an object to cycle its color; press and drag to move it.

Automated runs can drive the pointer without a mouse: `PointerInput.Instance.Inject(ray, pressed)` (editor / development builds only) feeds a world-space ray through the same code path as the devices. Example used in testing: inject a ray from the camera to the button with `pressed = true`, then the same ray with `pressed = false` a frame later.

> The Pipeline `simulate_pointer` command is not reliable here: it queues events on the real mouse, which the native mouse overrides on the next update, so a held press never shows up.

### visionOS simulator
Mouse clicks in Apple's simulator window are gaze + pinch, so the button and the objects can be used directly. The Claude desktop panel only displays the simulator; it cannot send input to visionOS.

### Multiplayer
With Multiplayer Play Mode (deactivate the Meta XR Simulator first), one player presses *Enter Room* and the others load the room too; colors and positions sync across players.

## Crash and force-quit recovery

A crash or force-quit (simulator `terminate`) skips the session leave, so the service still lists the player in the old session. `SessionManager` handles this on the next start:

1. `GetJoinedSessionIdsAsync` lists the stale memberships. A session the player hosted alone is deleted; otherwise the player is removed from it. Quick Join can then find or create a healthy session (the same one, if others are still in it).
2. Sessions carry a `ready` property that the creator flips to `1` only after Netcode is connected, and Quick Join filters on it. A creator that dies between creating the lobby and starting the network therefore never leaves a joinable session that nobody can connect to.
3. The Distributed Authority allocation can take minutes to fail inside the SDK (its default timeout is 315 s), typically right after a crash while the service still holds the old connection. `SessionManager` abandons an attempt that has not finished within 30 s, cleans up and retries (up to 4 times); the status panel shows *retrying*.
4. `AppBootstrap` spawns the session objects only once the local client is approved. Netcode fires `OnSessionOwnerPromoted` during approval, when spawning is still rejected; a rejected spawn used to leave an unspawned instance behind that blocked every later attempt, which is why the button could stay on *Connecting...* forever. Spawning now waits for approval and clears such leftovers.

Verified in the visionOS simulator with four launches in a row, three of them after a force-quit: each ended in a working session within 15–50 s (one needed the 30 s watchdog and a retry).

## Known limitations

- Drag keeps the object at the same distance from the viewer along the pointer ray, so sideways drags also change depth a little. A table-plane constraint and real grabbing (XRI) are Phase 3 work.
- No physics on the table objects yet; they can be dragged through the table.
- Quest bare-hand pinch uses the Meta aim pose; untested until a headset is available.

## PolySpatial gotcha

In the editor and on visionOS, PolySpatial keeps mirror GameObjects (named `… - PolySpatial id N`) with copies of our colliders at the same place. A plain `Physics.Raycast` can land on a mirror, which carries none of our components. `PointerInput` therefore uses `RaycastAll` and prefers the nearest hit that belongs to a `PointerInteractable`.
